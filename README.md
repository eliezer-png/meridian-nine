# Meridian Nine — scroll-scrubbed camera flight

A landing page where scroll drives a camera. The visitor scrolls; a pre-rendered camera flight
plays through six scenes of a (fictional) luxury watch manufacture, from an alpine building at
dawn to the watch itself. The page does not animate anything itself — it scrubs video by scroll
position, the same technique behind Apple's scroll-through product pages.

Built with the `scroll-world` skill, but with one significant substitution: **the camera flight
is synthesised locally rather than generated by a video model.**

## Run it

```bash
./serve.sh          # http://localhost:8787
```

Any static server works. The engine fetches each clip as a Blob and plays it from an in-memory
object URL, so it does not need the host to support HTTP byte-range requests — the usual cause
of a scrub-scrubbed video appearing frozen at frame 0.

## How the film was made

The intended pipeline renders each camera move with a video model (Seedance 2.0 via Higgsfield
or Monid). That was unavailable — no funded backend — so the six legs are **procedural 2.5D
camera moves computed from the six stills**.

| Stage | Tool | Output |
|---|---|---|
| Scene stills | Runway `nano-banana-pro`, 2752×1536 | `stills/still_1..6.png` |
| Camera design | by hand, per scene | `camera-paths.md` |
| Camera flight | `render25d.py` (numpy + PIL) | `site/assets/vid/leg*.mp4` |
| Encode | ffmpeg, crf 20 `-g 8` (desktop), crf 23 `-g 4` (mobile) | same |
| Page | `scroll-world` scrub engine, unmodified | `site/` |

### The warp

Each frame is an inverse warp of the still through the pinhole magnification law:

```
a point at depth Z, after the camera advances by d, magnifies by  m = Z / (Z - d)
```

Near pixels magnify faster than far ones — that difference is parallax, and it is what
separates this from a zoom. Depth is **analytic, not estimated**: every scene is a
single-vanishing-point composition, so depth is a smooth function of radial distance from the
vanishing point, plus a sky lock on the one exterior. No neural depth model is involved (none
would fit on a 4-core / 8 GB machine anyway).

Each leg specifies how much the *target* grows and how much the *edges* grow; the depth model
is solved backwards from those two numbers. Because a forward dolly only ever magnifies, the
inverse warp never opens a disocclusion hole — which is exactly why this is safe for a
forward-only chain and would tear immediately if the camera pulled back.

### The seams

Architecture A: one continuous forward take, six legs, no connectors, camera never reverses.

Six different photographs cannot hand off frame-identical pixels, so the chain matches
**luminance** instead of content. Every leg ends pushing into a blown-out light or into black,
and the next leg opens on that same value; the camera appears to pass through the light into
the next room. The seam values follow a deliberate exposure curve — cold outside, warm craft,
cool lab, warm boutique, black for the product. See `camera-paths.md`.

## Honest limitations

- **No reveals.** Nothing opens, parts or transforms. Every leg is a camera move over a fixed
  photograph.
- **Bounded travel.** Past roughly 1.7× magnification the warp softens and edges stretch; the
  per-leg values are set under that ceiling deliberately.
- **Gentle parallax.** A single radial depth field cannot separate a near verge from a building
  facade the way a true depth map would.
- **Seams are dissolves,** not unbroken continuations. Scrub slowly across one and you will
  read it as a cross-dissolve through light.
- **Mobile clips are centre-crops** of the 16:9 frames, not a native 9:16 composition. A true
  portrait version needs portrait stills and a second render pass.

## Re-rendering

Camera moves are cheap to change — edit the `LEGS` table in `render25d.py` and re-run:

```bash
python3 render25d.py          # all six legs, ~10 min on 4 cores
python3 render25d.py 3        # just leg 3
python3 render25d.py 3 --preview   # first/middle/last frame only, seconds
```

Requires `numpy` and `Pillow`.
